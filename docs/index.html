Understood as
objective:   POST cancel-order endpoint in the Express API; a cancelled

constraints: MUST keep existing tests passing; MUST NOT add dependencies

contract:    in: order id (+ caller identity) / out: order status + refund
             status / on_error: unknown order, not cancellable, refund failure
pattern:     idempotent (a retried cancel must never refund twice)

The repo is nearly empty, so I can't infer these from the code. There is no
Express app, no order model, no payment code and no tests.

3. Storage and auth: where do orders live, and who may cancel: the owning

   shared code?

Once you answer, I'll save the program to juxt/cancel-order.juxt and build it.

Language
The language. Small, strict, readable.
Five layers of intent, the words of every serious spec, six ways agents work together, and the checks that stop unsafe programs before they run.



  

    

      
01 · Language

      
Five layers of intent. Every keyword comes from engineering practice.

      
An architect can read a Juxt program cold. Context from C4, constraints from RFC 2119, contracts from design by contract, agents and handoffs from the multi-agent playbook.

    

    

  






  

    

      
02 · Requirement levels

      
The words of every serious spec, plus OPEN.

      
Models fill gaps with plausible guesses. OPEN turns each gap into a question. In 2.0 it can be routed to a person or to another agent.

    

    

      
MUST
Absolute requirement, checked against the diff by the reviewer and the harness.
shorthand !

      
MUST NOT
Absolute prohibition. Off-limits files, tools, APIs, data.
shorthand !!

      
SHOULD
Recommended. Any deviation is written to the decision log with a reason.
shorthand ~

      
OPEN
Unresolved. -> ask a person, or -> ask billing to query an agent.
shorthand ?

    

  






  

    

      
03 · Topologies

      
Six ways agents work together. One line each.

      
Pick the shape that fits the job. Juxt checks the shape for you: parallel agents need disjoint scopes, every handoff needs a typed payload, every loop needs a limit.

05 · Linter

      
Unsafe agent systems fail before they run.

    

    

      
W001missing-verifyNo verify block. Unverified output is a guess.

      
W007non-normative-terms"Production-ready", "perfect" or "10x" in an objective.

      
W002unmeasurable-objective"Better" or "robust" with no acceptance criterion.

      
W008unbounded-topologyTwo or more agents, or any loop, with no limits.

      
W003unscoped-agentAn agent with write tools and no scope.

      
W009unquarantined-input2.0Web, email or file content reaches an agent with write tools. Prompt injection risk.

      
W004scope-collisionParallel agents whose scopes overlap.

      
W010unsigned-remote-agent2.0An a2a:// agent without a signed agent card.

      
W005implicit-assumptionA fact with no source in context. Mark it OPEN.

      
W011untyped-handoff2.0A ⇒ handoff with no payload fields. Agents pass whole transcripts.

      
W006self-reviewA reviewer sharing the builder's context.

      
W012dark-run2.0A multi-agent program with no observe block. Failures can't be traced.

      
W013stale-stack3.0A dependency older than its freshness policy allows.

      
W016fleet-without-canary3.0A fleet change with no canary wave and no stop condition.

      
W014boundary-violation3.0A change crosses a context boundary the architecture denies.

      
W017pattern-incomplete3.0A saga step with no compensation, an outbox without a relay, and similar.

      
W015weakened-inheritance3.0A service relaxes a MUST it inherited from its domain or org.

      
W021uncited-claim3.2A narrative sentence in a status view with no fact behind it.

      
W022unapproved-broadcast3.2A view that emails leadership or customers with no approval step.

      
W019cache-without-invalidation3.1An answer cache with no ttl or source-change rule. Serves stale answers.

      
W020unchecked-program3.1A compiled T1 program serving numbers without a data freshness check.

      
W018residency-violation3.0An agent, model or log sink outside the data's declared region.

Architecture
Patterns your architects trust, enforced on every agent.
Boundaries agents cannot cross, the enterprise pattern catalog, fleet scale across hundreds of repos, and standards set once for the whole org.



  

    

      
01 · Architecture as code

      
Boundaries agents cannot cross.

      
Declare bounded contexts, who owns which data, and which dependencies are allowed. Every agent change is checked against it, so a fast agent can't quietly turn your services into a distributed monolith.

    

    

      
architecture.juxt

      

        
        
W014 boundary-violation · orders reads billing.db. Use events(order.placed) or the billing API. Change blocked.

      

    

  






  

    

      
02 · Pattern catalog

      
Enterprise patterns, enforced instead of documented.

      
The classic integration and resilience patterns your architects already use, plus ten new patterns for teams that build with agents. Applying a pattern adds its constraints and its checks, so a saga without compensation or an outbox that publishes inside the transaction fails lint.

    

    

      
      
    

    

      

      

    

  






  

    

      
03 · Scale and distribution

      
One program. Hundreds of repos. Many regions.

      
Juxt treats agent work like distributed systems work: idempotent tasks, queues, retries, durable checkpoints and explicit data boundaries.

    

    

      

        

        
queuedin progressverifiedretry → dead-letter

        

      

      

        
Fleet targeting
One program, every matching repo. Owners from CODEOWNERS get the PRs.
fleet: repos(org: acme, tag: java-service)

        
Agent pools
Workers pull idempotent tasks from a queue, with retries and a dead-letter queue.
scale: builder x 16, retry: 3 backoff

        
Durable runs
Checkpoints at every handoff. Long migrations survive restarts and resume days later.
harness: durable, checkpoint: handoff

        
Data residency
Agents, models and logs stay in the region the data belongs to.
data: residency(eu), models: allow(eu)

        
Cross-org agents
Partner and vendor agents join over A2A with signed cards and typed contracts.
remote agent ledger = a2a://… (signed)

        
Cost governance
Budgets per team and program, chargeback from traces, hard stops at the cap.
budget: team(payments) $2k/mo

      

    

  






  

    

      
04 · Governance at org scale

      
Standards set once, inherited everywhere.

      
Context federation lets the platform team set org rules, domains add their own, and services add specifics. A MUST set above can never be weakened below.

    

    

      
org.juxtSecurity policy, model allowlist, residency, approval roles, golden paths.

      
payments/domain.juxtPCI scope, idempotency on every write, saga for multi-step money movement.

      
refunds/service.juxtService context, owners, SLOs, local constraints. Inherits everything above.

    

    

      
Approvals by role
Who can approve what, mapped to your org chart.
approval before prod by role(architect)

      
Audit trail
Every agent action, tool call and approval traced and attributable.
observe: audit(retain: 7y)

      
Sensitive data
PII redacted before it reaches a model, checked at the harness.
policy: redact(pii) before model

      
Ownership
Every service has an owner and an on-call; agents route questions there.
owner: team(payments), oncall: pd(pay)

03 · Altitude · new in 3.2

      
Record it once. Every audience gets its own view.

      
Commits, tests, deploys, ticket moves and incidents are already facts. Today people re-tell them five times: in Jira, at standup, in an email to their lead, in a leadership status and on a dashboard. Juxt records each fact once in a ledger, then compiles every update from it at the right altitude. Jira and dashboards cost nothing; a short narrative uses a small model and must cite its facts.

Research
Research and the road ahead.
What the market is building, how Juxt fits on top of the open agent stack, and what it is ready for next.



  

    

      
01 · Market signals

      
The next "language" is intent, rules and checks.

      
Four movements in the market point the same way: people describe outcomes, agents write the code, and the durable artifact becomes the specification. Juxt is built to sit exactly there.

    

    

      
2025–2026
Spec-driven development
Tools such as GitHub Spec Kit, AWS Kiro, OpenSpec and Tessl move from prompt-then-code to spec, plan, tasks, code, with the spec as the source of truth and code as a compiled artifact.
Landscape map · Spec frameworks for Codex

      
Dec 2025 →
Agent Skills became a standard
The SKILL.md format started in Claude Code, was published as an open standard, and is reported in 30+ tools including Codex, Gemini CLI, Cursor and Kiro, now under the Linux Foundation's Agentic AI Foundation.
Agent Skills open standard

      
2025–2026
Protocols for tools and agents
MCP connects agents to tools and A2A connects agents to each other; both are open standards hosted by the Linux Foundation, with A2A at v1.0 and 150+ supporting organisations.
Linux Foundation · Protocol stack

      
2026
Intent-first platforms
Platform vendors now ship agent modes and workflow builders where developers describe outcomes and review agent output, with security and logic errors named as the open risk.
TechRadar on intent-first

    

    

      
Our read

      
General-purpose languages are not going away; they become the compiled output. The layer above them is forming now, and today it is fragmented: specs in one tool, skills in another, protocols underneath, no shared way to say what must be true and how to check it. Juxt's bet is to be that layer, portable across agents: compile to the skills and commands each tool already has, ask instead of guess, verify instead of trust, and record what it saved.

      
This is a reading of public sources, several of them secondary; adoption figures are as reported by those sources.

    

  






  

    

      
02 · Where Juxt sits

      
On top of the open agent stack, not instead of it.

      
MCP connects agents to tools and data. A2A connects agents to other agents, across teams and companies. Both are open standards hosted by the Linux Foundation. Juxt describes the work; the protocols carry it.

    

    

      
YouObjective, constraints, approvals. Read the diff, not the chat.architect

      
Juxt programAgents, topology, handoffs, policy, verification. Versioned with your code..juxt

      
Juxt IRThe exact prompt per agent: tokens, order, cache breakpoints, cost.juxt render --ir

      
HarnessRuns the loop: sandbox, hooks, checkpoints, resume. Enforces policy in code, not in the prompt.Claude Code · Agent SDK · Codex

      
AgentsRoles, models, scopes, memory. One context window each.agent

      
MCPAgent to tools and data: repos, databases, APIs, files.mcp://

      
A2AAgent to agent: signed agent cards, tasks that pause for input and resume.a2a://

    

  






  

    

      
03 · Built for what comes next

      
Ready for longer runs, more agents and stricter trust.

    

    

      
Protocol-native
Tools over mcp://, agents over a2a://. Adapters for new protocols, never lock-in to one vendor.

      
Model routing
model: auto(cost < $1, reasoning: deep) picks the right model per agent as models change.

      
Long-running agents
Checkpoints and resume. Pause states map to A2A tasks that wait for input or auth, then continue.

      
Signed identity
Remote agents need signed agent cards. Every handoff carries who sent it and is traced end to end.

      
Secure by default
Untrusted input is quarantined, tools are least-privilege, and policy is enforced by the harness, not by asking the model nicely.

      
Evals as tests
eval suites run in CI whenever a .juxt file changes, so a prompt edit can't silently break a team of agents.
